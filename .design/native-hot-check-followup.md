2026-10-07，按用户“不要什么都做”的要求，本轮先收敛到三项：

1. 根据远端 trace 修复 Chromium 修饰键链接测试的失败原因，保持真实浏览器行为断言和 flaky 门禁。
2. 用连续编辑、错误恢复、项目轮换和缓存回收检查常驻资源是否稳定；区分工作集、私有内存和 GC 后存活堆。

暂不做 PGO、SIMD、WebStorm 共享代理、跨服务持久化缓存或泛化并行调度。所有试验在主目录的任务专属临时目录完成，保留可复现的脚本和精简报告，清理临时夹具、trace、profile 和子进程。阶段完成后提交并推送，完整矩阵交给并行 CI。

### 公平比较：两边都使用原生增量

原先约 21 倍的比较包含了“完整冷检查 → 增量检查”的收益，不能全部归功于常驻。新的对照使用相同临时工程、相同正式 SDK、完整示例 TSX 配置和相同源码修改：独立 CLI 与常驻服务各持有自己的增量缓存，交替执行顺序。CLI 每次均重新启动进程，命令为 `tsc -p <config> --noEmit --incremental --tsBuildInfoFile <独立缓存>`。

| 场景                     | 独立 CLI + 原生增量 | 常驻 + 原生增量 |
| ------------------------ | ------------------: | --------------: |
| 首次无缓存，各一次       |             4.312 s |         4.873 s |
| 无变化，三次中位数       |              219 ms |           24 ms |
| 修改常量，三次中位数     |              234 ms |          192 ms |
| 类型错误，各一次         |              229 ms |          214 ms |
| 修复类型错误，各一次     |              224 ms |          232 ms |
| 修改真实 JSX，三次中位数 |             2.216 s |         1.930 s |

未清空 OS 文件缓存。这是小型受控工程的本机对照，不外推到所有项目。原始数据见 `reports/native-lifetime-comparison.json`。首轮临时脚本错误预期 CLI 的错误退出码为 1；查明增量信息已生成时为 2，修正断言后完整重测，仍严格验证 TS2322 和修复成功。

TypeScript 原生增量将项目图信息保存在磁盘，不要求我们维护脱离调用方存活的服务；缓存可由编译器重建。参见 [incremental](https://www.typescriptlang.org/tsconfig/incremental.html)。当前包构建已经使用原生 `-b`，可以保留。

### 收益边界与实际成本

刚完成的热检查分段计时，中位数 1.978 s，其中原生增量 build 请求约 1.843 s，额外依赖快照创建约 58 ms。常驻没有消除主要类型检查成本。CPU 样本包含 Windows syscall/IPC 等待栈，不能把累计百分比直接解释为独占墙钟阶段。

压力探针直接实例化生产 `NativeWorkspace`，复用同一个 Go 进程，省去外层 Node IPC。20 个项目轮换、240 次编辑和 24 次虚拟错误/修复均完成；空闲编译引擎保持 4 个，但每批 60 次编辑后的 GC 存活堆约为 26.1、37.1、43.3、55.9 MiB。Node 存活堆约 11.3–11.8 MiB。这个窗口尚未证明 Go 内存收敛，可能有缓存/延迟回收等原因，不能凭四个样本判定泄漏。原始结果见 `reports/native-hot-check.json`，不与此前主工作区 423 MiB 工作集混用。

现有后台方案实际需要维护启动锁、端点版本、独立 Node broker、多客户端租约、全工作区文件监听、额外磁盘指纹、缓存淘汰、停止确认、异常重连及旧进程退出。过去验证已经修复过 Windows 退出目录占用、路径身份和 pnpm 硬链接元数据误报，说明成本并非纯假设。`client.ts`、`server.ts` 和 `service-policy.ts` 合计约 381 行，此外还有 `workspace.ts` 中的共享/淘汰分支；这些行数仅说明范围，不等于能够原样删除的全部代码量。

### 建议的精简边界（待实施）

- 一次性检查、CI 和包构建直接使用定制 TS7-Go CLI，任务结束即退出。先保留完整检查，原生磁盘增量是可以独立选择的低成本能力，不新增自有缓存协调层。
- `vite dev` 持有自己的编译会话，开发服务器退出时释放；`vite build` 在一次构建内复用 Program，完成即释放。避免每个源文件都重新启动 Go。
- WebStorm 继续管理自己的原生 LSP。MCP/Node 工具由当前宿主持有 Go 子进程，宿主结束时关闭；保留必要的正常取消、错误与资源释放验证。
- 移除跨独立命令共享的 detached broker、发现/启动锁、空闲 TTL/LRU、跨客户端租约和专属 status/stop 管理。不把它们作为可选 daemon 长期保留，否则维护成本仍在。只把保留时间缩短为零不足以达到目标。
- 保留独立正确性修复，包括继承 paths、Windows 源码真实身份、声明/框架诊断、未保存输入边界和浏览器测试补强；不整体反向撤销提交。
- 不继续本轮 PGO、SIMD、通用 checker 改造或 IDE 进程共享。移除后台不是移除定制 Go 编译器，也不要求重新引入传统编译路线。

该方向接受少量重复进程启动/解析，以换取明确的所有权和更小的故障影响范围。Vite/LSP 的长会话仍要管理资源；缩小生命周期不等于自动消除所有潜在问题。
