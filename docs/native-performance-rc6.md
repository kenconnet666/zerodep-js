# RC6 编译性能与 TS-Go 源码研究

后续的[类型检查深入研究](typecheck-investigation.md)定位了按需绑定机会，并补充了不带统计参数的普通 CLI 测量。`--extendedDiagnostics` 会在记录内部耗时后强制执行两次 GC；本文带该参数的命令墙钟时间包含这部分开销，内存为回收后的存活堆。

2026-10-07，在主目录的 `853d39d` 上测量。定制 SDK 为 `7.1.0-dev.20261005.1+zerodep.native.52064eee65b8`，固定 TypeScript 源码提交 `50d70a3f5f453a79a4323b263165da51f656a4e3`。本次只新增研究记录；正式编译器、类型、配置和发布产物没有修改。

原始样本、命令、SDK 摘要及实验细节见 [JSON 记录](../reports/native-performance-rc6.json)。这些是当前版本的本机测量，不与旧 Babel 对照数据混用。

## 检查器数量并非越多越好

以 `node scripts/native/tsc.mjs -p apps/example/tsconfig.json --noEmit --extendedDiagnostics --checkers N` 交错运行 4、2、8、4、8、2、2、4、8。

| checker 数量 | 命令耗时中位数 | 编译器内部耗时中位数 | 编译器报告内存 | 类型实例化次数 |
| ------------ | -------------: | -------------------: | -------------: | -------------: |
| 2            |       11.514 s |             10.747 s |      531.6 MiB |      7,852,054 |
| 4（默认）    |       11.709 s |             10.867 s |      713.4 MiB |     10,436,278 |
| 8            |       12.786 s |             11.668 s |    1,224.8 MiB |     18,061,134 |

内存是 `extendedDiagnostics` 的统计，不是整个进程树的峰值 RSS。两线程比四线程的时间差很小、范围重叠，内存约少 25.5%；八线程则明确增加重复计算。另一次单 checker 探测内部耗时 13.399 s，仅作为方向参考，不与三轮中位数当作同等证据。

建议保留默认值，先在实际 CI runner 上比较二和四，再决定是否针对该工作负载调整；不全局增加到八。`--builders` 与 `--checkers` 会叠加并发，也需按项目依赖关系和内存限制调节。微软对这种重复工作和并行控制有[明确说明](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0-rc/#checker-parallelization)。

## 源码与 profile 的对应关系

核对了本地 TypeScript checkout 的以下文件，与 SDK 固定提交相比没有差异：

- `tsc/internal/compiler/checkerpool.go`：每个 checker 拥有自己的 symbol/type/instantiation 缓存。已有按依赖图关联文件的 weighted FENNEL 分配策略，平衡缓存复用与关键路径；相关权重已按多种真实项目校准。它已经包含在当前 SDK，不是尚待补入的优化。
- `tsc/internal/checker/checker.go:22532`：`instantiateTypeWithAlias` 有活动 mapper 缓存；`:22942` 的条件类型实例化按类型参数与 alias 等形成键并缓存。`:24803` 起还有确定分支的提前判定和适用条件下的尾递归循环处理。
- `tsc/internal/checker/relater.go`：类型关系查询已有缓存和递归控制。不能以简单的跨 checker 全局 map 替代这些结构；类型身份和检查上下文必须保持正确。
- `tsc/internal/project/checkerpool.go`：语言服务诊断、临时查询和 API checker 分工明确，API checker 保持稳定类型身份。共享进程/AST 并不意味着每个操作都共用一份类型缓存。

CPU profile 中，`instantiateTypeWithAlias` 的累计采样占比为 58.87%，其条件类型路径也很重；该调用树占累计分配空间约 87.24%。这些累计项目相互包含，不能相加；CPU 采样跨线程合计 30.49 秒，也不能当作墙钟时间。它表明优化应优先减少实例化和随之产生的分配。

单 checker trace 将最大检查事件定位到 `apps/example/src/workspace/Pages.tsx:219` 的 `<Link to={routes.tasks}>`，约 6.665 秒；`App.tsx:53` 的包装 `Button` 也较重。该事件包含共享缓存首次构建与追踪开销，不能解释为每个 Link 都固定花费这些时间。类型记录中，`jsx-runtime.d.ts` 的 `Equal` 两个泛型函数声明各关联约 41,308 个类型记录，`WritableKeys` 的映射声明也有相近数量。这与原生 DOM 属性推导、泛型组件和绑定属性检查的交互相符。

## 有效果的隔离实验

仅复制 `packages/use/dist` 到临时目录，通过临时 `paths` 让同一主示例使用副本。对照组和实验组使用完全相同的模块路径，原工程及其 `dist` 均未改动。

实验将 `LinkProps` 中固定的原生锚点属性提取为接口，再与泛型路由参数组合：

```ts
interface LinkAttributes extends Omit<NativeProps<HTMLAnchorElement>, 'href'> {}

export type LinkProps<R extends AnyRoute> = LinkAttributes &
  RouteOptions<NoInfer<R>> & {
    // 原字段保持不变
  };
```

| 指标，三轮中位数 | 原类型对照 |   接口实验 |
| ---------------- | ---------: | ---------: |
| 命令耗时         |   11.743 s |   10.698 s |
| 编译器内部耗时   |   10.849 s |    9.854 s |
| 分配次数         | 27,718,453 | 19,707,184 |

命令耗时约减少 8.9%，分配次数约减少 28.9%；类型实例化总数只从 10,436,278 降至 10,270,404，因此收益不能简单归因为实例化计数大幅下降，类型关系/中间结构的计算与分配也可能受影响。

六次主示例检查全部成功；现有 `packages/use/test/router.types.tsx` 对实验声明也通过，涵盖正确用法、必填路由参数、错误参数及事件 `currentTarget`。这还不是完整的声明兼容性、补全跳转或跨平台验收。微软也建议在合适的具体对象组合上使用接口以利用类型关系缓存，但该建议需要按实际类型结构验证，[性能指南](https://github.com/microsoft/TypeScript/wiki/Performance#preferring-interfaces-over-intersections)不是所有交叉类型都应替换的规则。

## 后续取舍

1. 优先把本次有收益的固定原生属性接口方案落到源代码，再做声明、绑定、路由及 LSP 回归。随后按 trace 判断是否推广到其他包装组件。
2. 若 DOM 属性推导仍重，再试验在库构建期从固定版本 DOM 类型生成可写属性信息，减少消费者重复运行复杂条件类型。必须保留只读属性限制、自定义元素扩展、事件类型与导航来源；目前没有量化收益，不直接全面生成替换。
3. 保持快照、Program 和已有诊断结果复用；让新增语义工具复用当前操作的 checker。现有 Go lint 已走调用方 checker，本次关闭它的单轮探测没有明显加速，保留启用。
4. 只有前述工作完成后 profile 仍暴露通用热点，才修改 Go checker 内部算法或文件分组策略；须用本项目及不同规模项目检查正确性、耗时和内存。本次没有证据支持改上游缓存键、删除类型安全检查或增加并发。

本次保留小型 JSON 和本文，任务专用的 profile、约 223 MB 类型 trace、声明副本及输出文件在提取证据后逐文件清理。
