# 常驻原生服务的可行性与实测

2026-10-07，延续[空 TSX 性能研究](empty-tsx-performance.md)。推荐在现有工作区服务上继续完善常驻与增量检查。原始记录与失败探针见 [empty-tsx-performance.json](../reports/empty-tsx-performance.json)。本轮只做研究，没有安装长期后台服务或改变默认生命周期。

## 已有基础及当前限制

当前实现已经包含 Node 工作区 broker、每个工作区的 Go LSP/API 进程、版本化本地 IPC 地址、编译会话及结果缓存。Windows 使用命名管道；服务标识包含根路径、SDK 摘要和 Node 适配代码摘要。CLI 工具、Vite 异步编译和项目 MCP 可以复用它。

目前尚不是适合跨多次独立命令长期复用的服务：

- `server.ts` 在最后一个连接断开后约 1.5 秒退出。
- `workspace.ts:dropShared` 在最后一个编译租约释放时关闭相应编译引擎和快照，即使其他工具连接仍存在。
- 完整 `check` 在输入变化或已有错误时释放旧快照，并通过 `createPrograms` 重新建项目，再获取完整语义诊断。未变化时有结果缓存，改动后仍有较高重复工作。
- 编译接口会更新快照，但检查的是请求文件；它不能替代完整项目及受影响依赖检查。

因此需要一起设计进程寿命、项目快照寿命和原生增量检查，而非只延长一个退出定时器。

## 同一 Go 进程的实测

独立临时工作区包含一个无 JSX 的 TSX 消费文件、一个依赖文件和一个全局声明。使用已安装的 RC6 SDK。修改依赖导出类型时，消费文件应出现 TS2322；该断言在完整检查和增量构建中均通过。

| 路径                        |    首次 | 无变化重复 | 修改依赖后 |   依赖错误/修复 |
| --------------------------- | ------: | ---------: | ---------: | --------------: |
| 当前共享服务完整 `check`    | 5.058 s |    15.0 ms |    4.144 s | 4.191 / 4.171 s |
| 共享 Go 进程 + 原生增量构建 | 4.701 s |    14.4 ms |    85.5 ms | 85.1 / 107.6 ms |

首次数据包含服务启动；增量构建首次另外删除任务自己的 build-info 后独立测量。错误/修复与第二轮增量样本使用已有缓存，不能把 86 ms 那次首次请求当作无缓存冷启动。所有记录包含 PID；同一测量会话内 PID 保持不变。

共享编译会话对单个常量文件检查并输出 JS：修改约 23 ms，类型错误约 22 ms，修复约 25 ms。加入真实 `<div />` 后首次约 1.885 s，再编辑 JSX 约 1.753 s。这条接口的检查范围是请求文件，不能与完整项目检查当作相同工作量，也不能声称所有 JSX 热更新都会在几十毫秒内完成。

释放编译客户端后观察到 `compileSessions`、`sharedProjects` 均归零，工具客户端仍在；随后所有客户端关闭，Node/Go 服务自动退出。统计中的 `programsCreated` 等是适配层计数，不代表 Go 解析器调用次数。

## 可以进一步统一的原生接口

当前固定 TS7.1 API 已提供：

- `createSnapshot({ openProjects: [configFile], ensurePrograms: true })`，由原生侧按真实配置打开项目。
- LSP 连接上的 `getCurrentLanguageServerSnapshot(...)`，取得并保留语言服务的规范快照。
- 原生 BuildOrchestrator 和磁盘增量信息，用于受影响项目/文件检查。

已用正式 SDK 冒烟验证前两项：按配置打开项目能正确加载继承的相对 `paths`；从同一个 Go LSP 取得两份保留句柄，配置项目 ID 相同、项目数保持一个，JSX runtime 已加载。两个快照句柄 ID 不同，不把这个观察解释为所有 AST/checker 对象必然同一实例。

本轮还发现现有适配边界：`parseConfigFile` 返回的继承相对 `paths` 直接传给 synthetic program 时，可能丢失定义这些路径的基准目录。首轮 daemon 探针因此没有加载 JSX 声明，后续 JSX 检查报 TS2875/TS7026；该轮时间已排除。性能重测使用绝对路径，随后另行验证 `openProjects` 能按原配置正确解析。正式接入应优先让原生项目系统处理配置，不能靠探针改成绝对路径来掩盖这个问题。

## 推荐的下一阶段

1. **保留现有 broker，增加受控的空闲保留。** 可以从几分钟、可配置的保留时间开始试验；项目快照也需要有界保留和内存淘汰。无客户端时不无限保留所有项目。SDK 或配置变化建立对应的新状态。
2. **完整检查接入原生增量路径。** 复用文件版本、依赖图与有效诊断结果，检查真正受影响的文件；保留配置、包元数据、声明文件和新增/删除文件的失效验证。当前每轮新建 BuildOrchestrator、复用同一 Go 进程与磁盘增量数据已有可用实测，不重新引入此前 Linux 验证失败的无限复用构建调度器方案。
3. **逐步统一配置项目与分析快照。** 让检查、lint、声明和编译尽量使用同一配置项目；仅输出选项不同的请求研究复用语义状态。存在未保存编辑、不同语义选项或不同项目时保留独立视图，结果标记对应源码版本。不能直接把编辑器未保存文本用于磁盘生产构建。
4. **后台检查与交互请求分开调度。** HMR 继续快速转换，类型诊断可后台增量更新；补全等交互请求保留优先级和取消机制。同一进程不意味着同一份类型缓存，上游 diagnostics/query/API checker 有各自职责。
5. **最后再评估 WebStorm 的进程共享。** 当前 WebStorm 自己启动 Go LSP，选择相同 SDK 不等于连接现有 broker。真正共享需要 LSP 代理或连接方式，并解决文档版本、多个客户端、取消与诊断分发。本轮没有验证这部分 IDE 集成，不将其作为先改善 CLI/Vite 的前置。

常驻与增量主要改善重复工作；首次冷加载和新用到的复杂类型仍有成本。前一轮按需绑定与本轮索引按需求值可以继续改善这部分，不以常驻进程替代类型算法优化。
