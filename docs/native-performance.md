# 原生编译器性能基线

这是删除传统编译器前的历史对照报告。当前 `pnpm benchmark:native` 只测试定制原生路线，输出 `reports/native-only-performance.json`；旧原始样本保留供比较，不需要重新安装旧工具。

2026-10-06，Windows x64 本机实测。原生后端显著减少纯转换时间；完整检查与输出有较小改善，带类型检查的增量编辑接近。不能将纯转换的十倍差异解释为整个应用构建或类型检查提速十倍。

## 结果

下表为耗时中位数，越小越好。两侧执行的工作在同一行内一致。

| 场景                                                           | Babel 后端 | 原生 Go 后端 | 观察                                                   |
| -------------------------------------------------------------- | ---------: | -----------: | ------------------------------------------------------ |
| 新进程内装载后端并首次转换四个 TSX 文件                        | 1,352.0 ms |     448.4 ms | 耗时减少 66.8%，约 3.02 倍速度                         |
| 常驻进程转换同样四个文件，含框架诊断、JS 与映射                |   235.4 ms |      23.6 ms | 耗时减少 90.0%，约 9.97 倍速度                         |
| 完整示例工程类型检查 + JS/声明/两种映射写盘                    |    16.55 s |      14.30 s | 耗时减少 13.6%，约 1.16 倍速度                         |
| 保留 Program 后修改 AuthoringExample，检查该文件并输出 JS/映射 |    2.512 s |      2.413 s | 约 4% 差异，波动区间重叠，不据此宣称类型检查有明显提速 |

热转换的 p95 为 Babel 335.9 ms、原生 28.6 ms；增量检查与输出的 p95 为 2.712 s、2.619 s。全量工程五轮范围分别为 15.35–18.10 s、14.17–14.89 s；五轮样本的 p95 实际就是最大值，不把它当作长期尾延迟估计。

两种全量构建均生成 108 个文件，即 27 份 JS、JS map、声明和声明 map。全部未压缩输出合计为 Babel 296,791 字节、原生 292,556 字节；这是编译产物与映射之和，不是浏览器下载体积。

## 内存

另行运行转换与完整工程负载，计入工作进程及子进程，包括 Go。Windows Toolhelp 发现进程树，读取 WorkingSet64，每次采样后等待 100 ms；实际采样间隔随进程枚举开销变化，原始记录包含次数和用时。下表是单轮采样峰值，不能等同于精确分配峰值，也不对几百分比差异作统计结论。

| 负载                            |  Babel 路线 |    原生路线 |
| ------------------------------- | ----------: | ----------: |
| 常驻转换四个文件，40 个测量批次 |   356.5 MiB |   105.2 MiB |
| 完整工程检查与全部输出          | 1,490.6 MiB | 1,408.9 MiB |

纯转换的内存差异明显；完整工程两侧都需要 TS7 检查器，内存仍在同一量级。最初使用 CIM 的采样器在本机产生超过一秒的查询开销，已替换为 Toolhelp 并重测内存；上面的计时数据始终来自没有内存采样干扰的单独运行。

## 方法与环境

- CPU：Intel Xeon E5-2698B v3，2.00 GHz、32 逻辑处理器；物理内存约 127.85 GiB；Windows 10.0.26200。
- Node 24.18.0、pnpm 10.34.5、Go 1.27.1、官方 TypeScript 7.1.0-dev.20261005.1。原生版本为 `7.1.0-dev.20261005.1+zerodep.native.3e8b0d4352f9`，完整源码和二进制摘要保存在原始报告。
- 每种场景五个独立进程，交替后端执行顺序。首次转换和完整工程每进程一个样本；热转换每进程预热三批后测二十批，共 100 个样本；增量每进程预热两次编辑后测六次，共 30 个样本。
- 四个转换文件为真实的 `AuthoringExample.tsx`、`TaskBoard.tsx`、`Pages.tsx`、`SharedPage.tsx`。没有以空文件或只含计数器的微型代码代表框架。
- 首次转换计时包含后端模块加载及首次转换，不包含父进程创建 Node、读取输入文件；未清空 OS 文件缓存，所以它表示冷进程装载，不表示冷磁盘。
- 全量测试使用完整 `apps/example/src`。Babel 路线先运行官方 TS7 的声明检查与输出，再由 Babel 输出 JS/map；原生路线运行一次原生 CLI，同时完成检查与全部输出。两者均落盘，不含 Vite/Rolldown 打包。
- 增量基线也保留官方 TS7 Program，只让它执行检查，再调用 Babel。原生使用同一快照中的检查与 JS emit。每次向真实源码追加不同的导出语句，使文件实际失效，不以重复文本的结果缓存冒充增量编译。
- 计时采样期间不并行执行本任务的测试或构建；这是正常使用中的桌面机器，没有独占 CPU、锁定频率或屏蔽其他应用。结果是本机基线，不是跨机器速度保证。

复现：先构建平台 SDK 和工作区包，然后运行 `pnpm benchmark:native --samples 5`。脚本将原始结果写到 `reports/native-performance.json`，清理临时配置和产物，关闭 Node/Go 服务。Windows 还运行独立的内存负载；`--memory-only` 可在相同 Node/编译器版本下保留计时数据并重新采样内存。

计时脚本见 [benchmark.mjs](../scripts/native/benchmark.mjs)、[工作进程](../scripts/native/benchmark-worker.mjs)和[Windows 内存采样器](../scripts/native/benchmark-memory.ps1)；完整样本见[原始 JSON](../reports/native-performance.json)。

## 使用取舍

原生 CLI 适合统一应用检查和组件库的 JS/声明输出；原生转换入口有明确的速度和内存收益。Vite 开发默认将类型诊断留给原生语言服务，框架语义诊断仍同步执行，避免每次 HMR 等待完整的文件类型检查；需要时可以显式启用 `typeCheck: true`。生产构建默认检查请求文件，整个项目仍可用 `zerodep-tsc --noEmit` 单独验收。

当前用户已选择单一原生路线，传统后端已经删除。性能历史数据不作为保留第二套实现的理由，也不自动代表当前工作区或其他平台的速度。
