# 类型检查热点深入研究

2026-10-07，延续 [RC6 初测](native-performance-rc6.md)。本次在主目录进行声明隔离实验，并从固定 TypeScript 提交及现有框架补丁构建临时 SDK。正式编译器源码、类型声明、SDK 和编译配置均未改变；没有创建工作树。所有原始样本、退出码、最小复现、SDK 摘要见 [研究数据](../reports/typecheck-investigation.json)。

## 结论与当前边界

已经找到比提取 `LinkAttributes` 更显著的优化机会：框架的 `LibraryManagedAttributes` 会让没有 `bind:` 的组件调用也计算完整的 `ComponentBindings<P>`。在 Go 诊断路径中根据 JSX AST 按需执行这部分推导，普通完整检查命令从三轮中位数 **11.514 s 降到 5.729 s**，约减少 **50.2%**。这仍是隔离原型，尚未安装或发布。

第一版无条件捷径导致空白位置的 `bind:` 补全消失，已据此修正为仅诊断阶段启用。修订版保留正常属性检查、泛型推断和相关负例；现有 core/use 类型用例通过，空白、`bi` 前缀、`bind:` 冒号后三种补全在诊断前后均保留。生产接入仍需严格验证框架命名空间归属、文件级 JSX 配置、属性展开、泛型和 API/LSP 查询复用；不能仅凭配置字符串就绕过任意 `LibraryManagedAttributes`。

## 为什么没有 bind 也会慢

调用链是：

```text
getJsxPropsTypeFromCallSignature
  → getJsxManagedAttributesFromLocatedAttributes
  → 实例化 LibraryManagedAttributes<C, P>
  → ComponentBindings<P>
  → BindableKeys、BindingChoice、Omit、交叉/条件类型及泛型推断
```

原实现位于固定上游的 `tsc/internal/checker/jsx.go`。`ComponentBindings<P>` 会枚举原始 props，匹配 `on${Capitalize<K>}Change` 回调，推导可绑定键，并组合普通 props 与绑定 props 的互斥分支。对于原生元素包装组件，props 本身已经包含 DOM 属性、事件、property 通道和模板字符串索引；对于 `Link`，又叠加路由泛型与必填参数条件。只确认最后没有可绑定属性，也可能先支付大量中间计算成本。

原型直接查看同一个 AST：没有 `bind:`，且没有可能携带绑定的属性展开时，诊断阶段检查原始 props；出现绑定或展开时保留完整路径。它不关闭类型检查，也没有移除用户的 `bind:` 能力。补全必须始终保留完整的候选属性视图，不能共用这个捷径。

## 最小输入与消融证据

每个消融变体只修改临时声明副本。移除功能的版本仅用于定位，不能作为可发布的性能优化。表中为编译器报告的检查阶段时间，多数为单轮探索值。

| 主示例变体                   |        检查时间 | 观察                                                       |
| ---------------------------- | --------------: | ---------------------------------------------------------- |
| 原始类型，两轮对照           | 10.204–11.010 s | 基准                                                       |
| 关闭声明文件自身检查         |        10.087 s | 仍需实例化实际用到的库类型，不能解决绑定热点               |
| 暂时取消 DOM 只读键判定      |        10.067 s | 类型对象从 125.7 万降到 22.5 万，但绑定关键路径仍重        |
| 暂时绕过组件绑定类型转换     |         5.216 s | 成本明显下降，但契约变弱，不能直接采用                     |
| 暂时去掉 Link 的泛型         |         5.268 s | 说明路由泛型与绑定转换的交互很重；不能以丢失参数类型换速度 |
| 同时取消绑定转换和只读键判定 |         2.294 s | 两项成本有交互，不能按单项差值简单相加                     |
| 仅提取 Link 固定属性接口     |         9.766 s | 有收益，但不是主要瓶颈的完整解决方案                       |

进一步把绑定转换精确替换为 `P`，主示例只出现预期的 `NameField bind:value` 类型错误，检查时间 5.014 s。这个失败样本保留在记录中，不能把它记为通过。

另一个最小复现是普通锚点包装组件：

```tsx
import { _component, type JSX } from 'zerodep-js';

const Anchor = _component((props: JSX.IntrinsicElements['a']) => <a {...props} />);
export const content = <Anchor href="/">内容</Anchor>;
```

原 SDK 在此独立配置下出现 TS2589（类型实例化过深），检查约 12.8 s；初版原生捷径通过，检查约 4.5 s。它说明大 props 的自动绑定推导不仅影响速度，也存在复杂度上限问题。此结果不代表所有带属性展开的调用都已解决，原型对展开仍走原有路径。

## 约六秒里面还有什么

修订后的诊断原型，三轮带统计参数的中位数为：

| 阶段                    |    时间 |
| ----------------------- | ------: |
| 解析                    | 0.087 s |
| 绑定符号                | 0.026 s |
| 语义类型检查            | 5.306 s |
| 编译器记录的 Total time | 5.433 s |
| 整条命令墙钟时间        | 6.025 s |

各列独立取中位数，不要求逐项精确相加。`--noEmit` 没有 JS 输出工作。差额包含进程生命周期和统计工作，尤其是 `--extendedDiagnostics` 的两次强制 GC。

核对 `tsc/internal/execute/tsc/emit.go:55` 后发现：编译器先记录 Total time，再执行两次 `runtime.GC()`，最后读取内存。因此早期报告的命令耗时不是纯粹的普通 CLI 时间，内存也应理解为两次 GC 后的存活堆，而非峰值 RSS。

已去掉统计参数重测，两个二进制使用相同标准库目录，均执行实际 `apps/example/tsconfig.json`，交错运行三次：

| 普通命令，无统计/profile |   中位数 |            范围 |
| ------------------------ | -------: | --------------: |
| 正式 RC6 SDK             | 11.514 s | 11.354–11.565 s |
| 仅诊断阶段按需绑定原型   |  5.729 s |   5.568–5.813 s |

重新采集不带统计参数的 CPU profile：类型实例化调用树占累计采样约 56.75%，条件类型实例化 53.94%，GC 扫描 23.69%，底层字节比较 `cmpbody` 的独占采样约 1.49%。累计调用树相互包含，不能相加或换算为独立墙钟阶段。CPU 采样共 18.15 s、采样窗口 5.50 s，包含多个线程工作。

剩余热点仍是大量条件/映射类型和中间对象。诊断原型仍创建约 **116.5 万个类型对象**，执行约 **1,010 万次类型实例化**；这比解析源文件更值得优先优化。

## 声明与 DOM 类型的固定成本

同一环境下，只有 `export const value = 1` 的 `.ts` 文件检查约 0.384 s；改为 `.tsx` 后约 4.2 s。`--listFilesOnly` 确认 TSX 多加载 JSX runtime、相关 core 声明及 csstype 等十个声明文件。它们总行数约 2.4 万，但不能把耗时仅归因于文本大小。

对空 TSX 再做消融，文件集相同：

| 临时变体                                             | 检查时间 |
| ---------------------------------------------------- | -------: |
| 原始声明                                             |  4.170 s |
| 取消只读键判定                                       |  1.843 s |
| 取消 `IntrinsicElements extends Elements` 的基类展开 |  2.495 s |
| 跳过全部声明文件自身检查                             |  0.001 s |

这定位到声明验证时对原生属性映射和只读条件类型的展开。最后三个选项都改变了验证范围或契约，不能直接用来宣称同等检查变快。实际主示例仍会使用这些类型；例如诊断原型加 `skipLibCheck` 后仍需检查约 3.94 s。

## 其他已经试过的方向

- `BindableKeys` 改成 key-remap 再取 `keyof`：检查从约 10.4 s 退化到 14.4 s，类型对象和分配均增加，放弃这条改写。
- 给回调键增加模板字符串交集、缓存可绑定键的中间别名：只有小幅探索收益，没有消除热点，不优先扩大改写范围。
- 没有宽泛索引签名时，绕过 `DeclaredMembers<T>` 重建：实例化减少，但实际耗时改善较小，也没有解决锚点包装组件的 TS2589。
- 直接在 Go 中识别当前 `WritableKeys` 别名并读取 `isReadonlySymbol`：三轮命令中位数 6.025 → 5.863 s，仅约 2.7%；类型对象总数完全未降，实例化仅减少约 3.5%。现有类型用例和八项补充键等价断言通过，但这处插入点收益不够明确，不建议按此原型增加正式分支。更合理的下一步是研究在泛型展开之前生成或缓存属性元数据。
- `GOGC=100/200` 各两次交错比较：区间重叠，没有稳定收益，保留默认。统计输出经过强制 GC，不能用它评估运行中的峰值内存变化。

补充等价用例覆盖普通/只读/可选成员、getter/setter、三类索引签名、交叉类型以及 form/select。初版用例错误地期待 `prop:name` 出现在 select 上，两种 SDK 均失败；按框架的模型属性排除规则修正预期后均通过，原始失败也保留在 JSON 中。

## SIMD、并行化与 PGO

Go 1.27.1 的字节比较已经使用 SSE，并在合适的 CPU 和长度下走 AVX2；内存清零和哈希也已有专门实现。Go 1.27 另有需显式启用的实验性可移植 SIMD API，支持 amd64、arm64 等平台，并提供模拟实现。[Go 官方说明](https://go.dev/blog/simd-experiment)

对初版按需绑定原型比较默认 AVX2 与 `GODEBUG=cpu.avx2=off`，每组两次：默认 6.147–6.194 s，禁用 6.030–6.165 s，没有可辨认收益差异。这个试验只比较现有 AVX2 分派，SSE 等路径仍可能执行，不能据此认定所有 SIMD 都无效。当前类型检查以对象图、缓存、分支和递归关系为主；更适合 SIMD 的扫描/批量比较只占较小部分。后续应按 profile 选出具体连续数据循环，独立比较标量与向量实现，而不是全局开启实验后声称编译器已向量化。

同一个原型也测试了 checker 数量：

| checker 数 |           命令时间 | GC 后存活堆 |
| ---------- | -----------------: | ----------: |
| 1          |            7.313 s |     351 MiB |
| 2          |            6.841 s |     513 MiB |
| 4          | 三轮中位数 6.004 s |     695 MiB |
| 8          |            6.456 s |   1,207 MiB |

1/2/8 是单轮探索，4 是三轮。修复关键路径后，并行化取舍会变化，因此不能沿用优化前“二和四相近”的判断。当前仍保留四；上游已有依赖图分组，增加 checker 会重复构建公共类型缓存。进一步的并行机会应优先考虑独立项目、构建阶段和经过度量的文件分组，不并发读写同一个有状态 checker。

PGO 可以根据真实 CPU profile 改善编译器的内联等决策，值得在类型结构稳定后，用 CLI、增量编辑和语言服务的代表性负载单独试验。本次没有构建 PGO 版本，不承诺收益。[Go PGO 文档](https://go.dev/doc/pgo)

## 推荐顺序和复现材料

1. 将诊断阶段按需绑定作为首要候选，补齐严格的框架归属判断、展开属性、文件级 JSX 配置和 LSP/API 回归，然后才合入正式补丁。
2. 深入处理 `NativeProps`/`WritableKeys` 的中间类型生成。候选为库构建期生成常见属性信息，或在定制 Go checker 的更早阶段原生查询可写键；需保留用户 DOM 扩展和 readonly 语义。当前晚阶段 alias 钩子的结果不足以支持直接采用。
3. 在新的类型结构上重测 checker 分组、内存和代表性 PGO；SIMD 只针对被 profile 证实的具体循环。
4. 完整声明检查保留为质量门禁；应用层是否另设 `skipLibCheck` 是检查范围决策，不与同等正确性优化混为一谈。

保留了[诊断原型补丁](../reports/typecheck-diagnostic-prototype.patch)和[只读键实验补丁](../reports/typecheck-readonly-prototype.patch)。它们是研究材料，未加入 `nativeInputs`，不会随正式构建应用。前者应用于固定上游加现有两份框架补丁后的源码，后者叠加在前者上；使用现有 Go 1.27.1、`-tags=noembed -trimpath` 构建到独立目录，复制同版本标准库后可复现实验。补丁中的路径/名称守卫仍是原型级，不能直接作为发布实现。

临时源码归档、SDK、声明副本、探针和 profile 在提取证据后按文件清理，正式 SDK 二进制摘要保持不变。
