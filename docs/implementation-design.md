# 实现路线、代价与设计约束

更新时间：2026-10-01。本文补充[生产化主计划](production-plan.md)的实现思路，配合[API 评审用例](api-review.md)讨论。以下是项目设计建议，不是已实现能力，也不新增本轮测试或实现任务。

## 1. 必须接受的基本取舍

目标是 `let count = $state(0); count++`，同时保持合法 TSX 和细粒度更新。这需要编译步骤：普通 JavaScript 函数无法拦截局部数字变量的后续读取和赋值，Proxy 只能处理经由对象的操作。类型声明也不会给变量增加运行时能力。

因此可以保留标准 TSX **语法和原生类型检查入口**，但必须明确哪些位置具有框架语义。不能同时承诺“所有代码完全遵循普通 JavaScript 的求值行为”与“解构后的局部变量自动持续读取最新 props”。普通位置保持普通语义，标记位置的特殊规则必须小而可解释。

| 路线                            | 使用形态                                                   | 主要代价                                                   | 本项目倾向                         |
| ------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------- |
| 运行时访问器                    | `const [count, setCount] = signal(0)`，读取 `count()`      | 显式读取和写入接口；不满足普通变量式读写                   | 机制可参考，不作为主 API           |
| 运行时响应式对象                | `const state = reactive({ count: 0 })`，读写 `state.count` | 每次通过对象访问；普通解构数字会取出当时的值               | 可作为对象机制参考，不替代变量方案 |
| 编译宏与明确组件边界            | `$state`、`$derived`、`component(...)`                     | 需要编译器、源码映射和框架诊断                             | 推荐                               |
| 所有 `let` 和普通解构自动响应式 | 不写显式声明                                               | 编译范围、数据流和调试规则更难解释，普通工具函数也受到影响 | 不推荐，违背显式声明方向           |

明确拒绝用运行时代理假装实现任意局部变量监听，也不靠执行整个组件来掩盖细粒度机制没有实现。若不接受编译成本，就需要回到前两种使用形态，而不是继续隐藏这个代价。

## 2. 组件边界为什么推荐 component

| 写法                                             | 优点                                         | 成本或限制                                               |
| ------------------------------------------------ | -------------------------------------------- | -------------------------------------------------------- |
| `component(({ step = 1 }: Props) => ...)`        | 同时提供明确编译位置与类型入口，适合参数解构 | 增加一层调用；泛型签名和诊断必须保留                     |
| 普通函数体首行 `"use component"`                 | 保留函数声明外形                             | 还需解决类型识别，且要说明这个字符串指令的语义           |
| `function Counter(...)`，按名称或 JSX 返回值推断 | 视觉上最少                                   | 重命名、辅助函数、重构容易改变识别结果                   |
| 函数体内 `$props<Props>()`                       | 响应式输入入口显式                           | 自然的参数类型被移到函数体，调用方类型还需另一条连接规则 |

推荐第一种，但不把名称本身视为不可改变的设计。组件品牌、调用约束和声明产物应作为阶段 1 的类型样例确认。

`component` 只负责组件身份、参数语义与生命周期入口；`$state` 等宏通过导入绑定在被编译的 `.ts` / `.tsx` 中识别，从而允许普通 `createCounter` 辅助函数复用状态。不能一方面展示组件外复用状态，另一方面只转换组件函数内部代码。

建议初版限制：参数顶层解构支持别名、默认值和 rest；深层解构先给明确诊断和替代写法，例如保留 `props.user.name` 或写显式派生。若决定支持深层解构，则先规定整个 user 对象替换时的行为，不能静默变成过期快照。

## 3. 编译器与 TS7 分工

```text
原始 .ts / .tsx
  ├─ TS7：原生类型检查、补全、重命名、声明输出
  └─ 框架编译器：绑定分析 → 宏语义 → JSX 结构分析
                         ├─ 客户端 DOM 输出
                         └─ 服务端 HTML 输出
       两条输出都保留源码位置，并由 Vite 完成开发和构建集成
```

建议使用已经安装的 Babel 8 先实现独立编译入口，再接 Vite。宏按实际导入的词法绑定识别，支持别名，尊重同名局部变量；不能按 `$state` 字符串全文件替换。

客户端和服务端共享必要的绑定及模板分析，分别生成目标代码。开始时只建立能解决重复逻辑的内部结构，不预先建设适配任意平台、任意 AST 后端的通用编译器架构。Babel、Oxc 等工具的历史调研见[研究记录](../.design/ts7-tsx-research.md)，后续换后端以真实瓶颈和兼容成本为依据。

建议的编译契约：

- 独立 `compile(source, filename, options)` 返回代码、source map 和结构化诊断；参数名和返回形态尚未冻结。
- 在 JSX 被提前降成普通调用之前完成动态表达式分析；避免与其他 JSX 转换重复处理。
- 编译依赖写在构建侧；浏览器运行时代码不得引入 Babel 或 Node API。
- 导出的函数、泛型组件、宏声明都用源代码生成可消费类型，不从私有 helper 输出反推用户 API。
- 宏模块未经过转换时应尽早给出可理解的错误，不静默退回普通函数而产生不更新的页面。
- 普通第三方依赖不做全量扫描改写；框架库优先预编译发布。需要消费源代码的特殊场景再规定插件边界。

## 4. 变量、依赖与副作用如何连接

源代码：

```ts
let count = $state(0);
const doubled = $derived(count * 2);
count++;
```

编译器将状态绑定连接到私有存储，将读取连接到跟踪函数，将赋值连接到写入函数；派生表达式变为按依赖求值的计算。这些内部函数名、容器和数据结构不进入使用者 API。

必须保持的细节包括：`count++` 返回旧值，`++count` 返回新值；`count += expensive()` 的右侧只执行一次；短路赋值不能无条件执行右侧；对象简写和闭包读取应转向同一个绑定。难以正确支持的语法应报错，不能生成“多数情况下能运行”的代码。

推荐调度基线，仍需在阶段 1 冻结：

- 状态写入立即生效，同一个同步调用里再次读取必须得到新值。
- 派生按依赖失效，读取时得到一致结果；纯派生内部不写状态。
- DOM 更新与用户 effect 区分。effect 究竟在挂载哪个时点首次运行、后续在哪个队列运行、是否需要显式 flush 入口，必须用行为样例决定。
- 重复同步写入可合并通知，但不能使 `count` 与依赖它的派生暴露互相矛盾的结果。
- 依赖跟踪只覆盖同步执行；跨 `await` 的读取、取消与过期结果由明确代码处理。
- 组件、条件分支、列表行各有所属作用域。清理责任随作用域传递，销毁是幂等操作。

普通函数调用仍然传当前值。`consume(count)` 不会凭空得到可持续读取的状态句柄；`consume(() => count)` 才能表达以后读取最新值。组件外调用一个创建 effect 的辅助函数时，还必须有明确的作用域或显式 disposer；不能产生无人负责销毁的订阅。

## 5. 对象状态不能只说“支持深响应式”

| 方案                     | 自然操作                             | 必须承担的语义                                         |
| ------------------------ | ------------------------------------ | ------------------------------------------------------ |
| 仅跟踪整个变量           | `user = { ...user, name: next }`     | `user.name = next` 不触发更新，需明确限制              |
| 普通对象和数组按属性跟踪 | `user.name = next`、`rows.push(row)` | Proxy 身份、别名、数组长度、键枚举、删除和替换都要定义 |
| 所有对象无差别代理       | 类、DOM、Map 等都经过代理            | 内部槽、私有字段、方法接收者和外部库兼容风险大         |

倾向第二种，并限制可代理范围。初版对类实例、DOM、Date、Map/Set 等保留原值，内部变动不会自动获得跟踪能力；需要时通过变量替换或日后明确的适配能力更新。准确范围应写成支持表。

对于 `const raw = { n: 0 }; let state = $state(raw)`，必须决定 raw 与 state 的对象身份及写入关系。推荐不暗中深拷贝用户对象；经状态代理的操作可以跟踪，通过原始别名绕过代理的写入不能承诺通知。是否采用此规则、是否提供浅状态或快照入口，均待评审。

props 只读意味着不能给输入绑定重新赋值，不等于递归冻结传入对象。子组件如需修改共享对象，必须有可解释的数据所有权约定；初版默认推荐通过回调交还修改意图。

## 6. 原生类型提示成立之前要解决什么

类型与框架语义不是完全等价的。例如下面是**风险反例**：

```tsx
const Profile = component(({ user }: { user: { name: string } | undefined }) => {
  if (!user) return null;
  return <button onClick={() => console.log(user.name)}>查看</button>;
});
```

若将 user 的每次读取改成实时 prop 读取，点击时 user 可能已经变为 undefined。TS 对原始局部绑定所作的收窄，不能证明转换后的每次读取仍然安全。与此同时，函数体初始化时的 `if` 不会自动变成持续更新的视图分支。这个例子同时暴露类型与执行次数两个边界。

建议明确：组件函数初始化执行一次；需要跟随变化的结构放在受编译器支持的 JSX 动态位置。回调里需要使用可选对象时，在当前执行里重新读取和判空：

```ts
function handleClick() {
  const current = user;
  if (current) console.log(current.name);
}
```

这里 current 是本次读取的局部引用，不是深度快照。可辨识联合的 mode/value 若有相关性，应一次读取完整对象并在同一次调用中判断，不能默认多个独立实时绑定永远保留这种关系。

阶段 1 必须先确定支持范围、写法和必要诊断；至少处理 props 写入、跨回调收窄、条件早退、泛型签名、children 与 rest。`.d.ts` 不能独自拒绝所有框架语义错误，source map 也不能修正类型检查器的控制流分析。无法给出可靠诊断时，应该缩小首版支持范围或选择明确的安全写法，而不是承诺“标准 TS 类型通过就一定语义正确”。

阶段 8 负责把已有契约完善成编辑器和开发流程体验，不能到阶段 8 才发现核心 API 无法兑现类型含义。

## 7. DOM、SSR 与 hydration 的共同契约

推荐编译成直接 DOM 操作和动态区域，避免一开始维护另一套完整 VDOM。代价是编译器和运行时必须共同掌握区域身份、插入锚点和作用域清理；这不是“没有 diff”，稳定 key 列表仍需要协调算法。

SSR 生成同一套组件语义对应的 HTML，hydrate 认领已有节点并建立订阅。三条路径要共同定义：

- 文本空值、数组/Fragment、条件区域、列表 key 和事件附着行为。
- 属性与 DOM property、表单初值、SVG namespace，以及浏览器修正非法 HTML 后的行为。
- 稳定 ID、默认值、初始数据和环境差异；不能让服务端与客户端各自生成不同随机初值。
- 服务端 scope 在请求结束或失败时释放；浏览器副作用不在服务端运行。
- mismatch 是报错、局部重建还是整根重建，以及生产环境如何观察该问题。

建议第一版同步 SSR、请求内取数后再渲染。框架不自动把所有服务端 props 序列化到页面：函数、循环引用和敏感服务端数据不能被一股脑塞进 HTML。初始数据传输需要明确、可审查的入口与转义规则。

CSR/SSR 的“自由切换”首先指应用入口可选择部署/请求模式：同一 App 在 CSR 使用 mount，在 SSR 页面使用 hydrate。已经挂载的单页应用要改变模式，可以导航后重新加载；不承诺无刷新把现有客户端实例变成服务端实例。

## 8. 包边界与成本控制

现在保留 core、ssr、example。当编译器和 Vite 插件开始有实际实现时，再按依赖边界建立对应包；公开包名和子路径在产物评审中确定。

| 职责        | 应包含                                 | 不应进入该依赖图                  |
| ----------- | -------------------------------------- | --------------------------------- |
| 浏览器 core | 响应式、DOM、组件、公开类型            | Babel、Vite、Node 服务端模块      |
| 服务端渲染  | 请求作用域、HTML 生成、必要 SSR helper | 浏览器全局访问、客户端 DOM 初始化 |
| compiler    | 语义分析、目标输出、诊断、source map   | HTTP 服务与应用业务逻辑           |
| Vite 适配   | 编译入口接线、开发诊断、HMR 生命周期   | 一份重复的语义转换实现            |
| example     | 真实消费、模式切换、代表性页面         | 为示例专门绕过公共 API 的私有捷径 |

`zerodep-js` 的名字不自动等于已经承诺所有包零依赖。推荐浏览器运行时优先保持无第三方运行时依赖，构建工具可以有依赖；是否将此作为硬性发布指标，应明确确认，不能为了名字重新实现所有工具。

当前不估算固定开发天数：编译语义、类型缺口和 hydration 的决定会直接改变工作量。先冻结关键契约、完成一个可审查的端到端组件，再依据实际交付速度估算剩余阶段；生产门槛不因工期压力降为“示例能跑”。
