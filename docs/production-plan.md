# zerodep-js 从基础工程到生产可用

更新时间：2026-10-01。

本文是后续讨论与执行的主计划，终点是有明确支持范围、可安装、可维护、经过真实使用验证的生产版本。它不是当前功能清单，也不因写入文档就把候选 API 视为已经实现或全部批准。

当前阶段按用户要求暂停追加测试和框架实现，先完成提交与规划。后续长时间自主执行，应在用户确认本计划和关键 API 决策后开始。

## 1. 目标与当前状态

已确认的方向：

- 使用标准 TypeScript/TSX，类型基线为 TypeScript 7，不增加 TypeScript 5/6 兼容层。
- 状态显式声明，之后像普通变量一样读取和赋值，不暴露状态容器 `.value`。
- 组件支持直接解构 props，并就近使用默认值。
- API 简洁、职责明确，不为形式增加 model、controller、factory、通用配置对象等层次。
- 支持 CSR 和 SSR；生产版本还必须具备与 SSR 对应的 hydration。
- 参考 Svelte、Solid、Vue 的具体机制，依据本项目的 TSX、类型系统和维护成本做选择。

| 领域 | 当前情况 | 距离生产可用还缺什么 |
| --- | --- | --- |
| 工作区与工具 | pnpm、TS7、Vite 8、Babel 8、Vitest、Playwright 已配置 | 持续验证和发布流程 |
| `packages/core` | 只有空入口 | 响应式、组件、DOM、公开类型 |
| `packages/ssr` | 文档模板组合、SSR/CSR 分发 | 组件 HTML 渲染、转义、hydration 协议等 |
| `apps/example` | 开发与生产入口、模式切换、原生 DOM 工程探针 | 用真正的框架 API 替换探针 |
| 语言服务 | 原生 TS7 MCP 五项工具已直接验证 | 框架专有诊断、完整编辑器体验 |
| GitHub | 公开仓库与基础 CI 已建立 | 阶段交付、版本发布和真实试点 |

目前的 SSR 页面可以在 JavaScript 执行前显示内容，但示例的原生事件接入不是通用 hydration。第三方工具接入测试和工程探针不能用作框架功能验收。

## 2. 第一版生产范围

首个生产版本面向现代浏览器与 Node 服务端，至少需要：

1. 变量式状态、纯派生、可清理副作用，以及可靠的依赖与生命周期管理。
2. 有类型的函数组件、响应式 props、默认值、children、事件和原生属性转发。
3. 文本、属性、条件、列表和动态组件的正确 DOM 更新。
4. 常见输入控件、焦点、选择区、IME 与组件销毁行为正确。
5. 同一应用的 CSR、SSR 与 hydration，保证服务端和客户端的语义一致。
6. 标准 TSX 编辑体验、可定位的编译错误、可用的 source map 和开发更新流程。
7. 可消费的包产物、版本策略、支持范围、文档和真实应用验证。

以下能力不默认成为首个生产版本的前置条件：内置路由、全栈数据层、RSC、流式 SSR、复杂 Suspense、动画系统、完整 UI 组件库、多个构建器适配、旧浏览器兼容。需要时单独确认，避免把生产可用扩大成无止境的功能清单。

## 3. 推荐 API 形态

以下是推荐的讨论基线。现有 core 没有这些导出。模块拆分与最终命名可以在实际实现前调整。

### 3.1 组件、props 与默认值

```tsx
import { component, $state, $derived } from '@zerodep-js/core';

type CounterProps = {
  initial?: number;
  step?: number;
  onChange?: (value: number) => void;
};

export const Counter = component(
  ({ initial = 0, step = 1, onChange }: CounterProps) => {
    let count = $state(initial);
    const doubled = $derived(count * 2);

    function increment() {
      count += step;
      onChange?.(count);
    }

    return (
      <button type="button" onClick={increment}>
        {count} / {doubled}
      </button>
    );
  },
);
```

推荐规则：

- `component` 明确编译边界，参数解构得到只读的响应式输入绑定。
- 支持就近默认值和重命名，例如 `class: className`；不要求单独维护 defaults 对象或运行时 props schema。
- 小组件允许内联 props 类型；复杂或复用的类型再单独命名，不强制拆文件。
- 保留 `component((props: Props) => ...)`，复杂关联类型或嵌套数据可以直接访问对象。
- 泛型包装保留原始函数签名，不把 props 压成 `any`。TypeScript 的泛型、联合、Pick、Omit、NoInfer 等直接使用，不另造类型 DSL。
- 组件通过 JSX 或根挂载入口创建；普通辅助函数继续普通调用。直接调用组件值的契约需要在第一阶段明确。

默认值必须在第一阶段确认下表，不能先实现一种再让用户猜：

| 情况 | 推荐语义 |
| --- | --- |
| 未传入或值为 `undefined` | 使用默认值 |
| `null`、`false`、`0`、空字符串 | 保留传入值；不是默认值触发条件 |
| 默认数组或对象 | 每个组件实例独立，不与其他实例共享 |
| 无响应式依赖的默认表达式 | 首次需要时计算并缓存，反复读取不重建 |
| 默认表达式依赖前面声明的 props | 推荐按依赖更新的缓存 fallback；时序仍需确认和专项验证 |
| 引用后面参数或形成循环 | 保持清楚的错误，不因改写而偷偷改变初始化规则 |
| 默认函数值 | 得到该函数，不自动调用函数体 |
| 默认值中建立订阅或发请求 | 不推荐；副作用放在明确的生命周期入口 |

“所有默认值永远只求值一次”不足以描述依赖其他 props 的情况。推荐使用统一的缓存 fallback 语义：无依赖结果保持稳定，有依赖时按实际读取更新；这个决定仍需在第一阶段冻结。

`$state(initial)` 只在创建状态时取一次初值，后续 initial prop 变化不自动重置用户状态。需要持续计算时使用 `$derived`。

### 3.2 状态、派生与副作用

```ts
let count = $state(0);
const doubled = $derived(count * 2);

const total = $derived.by(() => {
  let result = 0;
  for (const item of items) result += item.price * item.quantity;
  return result;
});

effect(() => {
  const stop = subscribeToSomething(id);
  return stop;
});
```

- 普通表达式保存执行时的结果，只有显式派生持续跟随。
- 派生绑定推荐只读；暂不引入临时覆盖派生值的双重数据来源。
- 普通对象和数组推荐支持属性级状态；类实例、DOM、Map/Set 等另定，不承诺一律深代理。
- 是否直接代理输入对象、原对象别名的行为、浅层状态入口和序列化方式必须明确。
- 普通函数传参仍传当前值；需要以后读取最新值时显式传 getter。
- 副作用跟踪同步读取，重跑前和销毁时清理。不能把任意 async 函数自动当成安全、可取消的响应式任务。

### 3.3 事件、属性与复用组件

```tsx
type ButtonProps = JSX.IntrinsicElements['button'] & {
  tone?: 'primary' | 'neutral';
};

const Button = component(
  ({ tone = 'primary', type = 'button', children, ...attrs }: ButtonProps) => (
    <button {...attrs} type={type} data-tone={tone}>
      {children}
    </button>
  ),
);
```

- 原生事件使用浏览器事件类型；准确提供 currentTarget，不借用 React SyntheticEvent。
- 回调 props 保持普通函数；组件业务事件按值传递，不强制创建事件总线或事件对象。
- `...attrs` 推荐为响应式的排除视图，必须处理新增、删除和值更新。
- JSX 属性遵循从左到右的覆盖顺序。class/style 的组合由明确代码或明确能力完成，不暗中合并任意属性。
- props 绑定只读不等于深度冻结对象。深层引用、共享可写模型和父子数据所有权需要清楚约定。
- `exactOptionalPropertyTypes` 下，可选属性与显式 undefined 有区别；需要透传 undefined 时在类型中明确允许，初版不通过复杂类型适配悄悄改变契约。

### 3.4 输入与状态复用

```tsx
let name = $state('');

<TextInput value={name} onValueChange={(next) => (name = next)} />;
```

受控 value 和初始化用的 defaultValue/initialValue 分开表达。是否同时支持受控、非受控以及切换模式，由具体组件契约决定；不要求所有组件套用一个通用 control 抽象。双向绑定语法在这个基础正确后再讨论。

```ts
function createCounter(initial = 0) {
  let count = $state(initial);

  return {
    get count() { return count; },
    increment() { count++; },
  };
}
```

先使用普通函数、getter 和操作方法暴露共享逻辑。普通 `return { count }` 保留取值语义，不自动改成 getter；也不为了减少几行出口代码马上增加多套宏。

### 3.5 条件、列表与 children

```tsx
<>{open ? <Panel /> : null}</>

<For each={rows} keyBy={(row) => row.id}>
  {(row, index) => <Row row={row} index={index} />}
</For>
```

列表写法是候选。必须先解决同 key 替换对象、排序保留状态、删除清理和 index 更新，才能批准回调参数的具体语义。若需要编译器把列表参数作为实时绑定，必须限定清楚识别位置；普通 map 和任意回调不能悄悄获得不同语义。

普通 children、可重复使用的内容工厂、带参数 render callback 要区分。JSX.Element 是类型黑盒，不能承诺仅靠它精确限制子组件种类。重复插入内容究竟创建新实例还是移动节点，必须先确定。

### 3.6 根挂载与服务端入口

```ts
const dispose = mount(App, { target, props });
const disposeHydrated = hydrate(App, { target, props });
const html = renderToString(App, { props });
```

这是推荐形态，尚未实现。mount/hydrate 推荐返回清理函数。首版优先同步组件渲染；服务端数据可以在调用渲染前准备。是否引入异步组件、流式结果或更多返回字段需要单独确认。

当前 `renderDocument` 只负责模板组合，不能替代这里的组件 renderToString。最终 mode 切换应当驱动同一 App 的 mount 或 SSR + hydrate。

## 4. 分阶段路线

每阶段完成定义都是未来执行的门槛，不表示现在已经完成。每个阶段包含实现、相关验证、文档更新、提交和推送；不把测试留到最后补。

### 阶段 0：工程基础与模式入口

状态：基础部分已完成。

- 维护 core、ssr、example 的职责与 workspace 依赖。
- TS7、Babel 8、Vite 8、Vitest、Playwright、LSP、锁文件和 CI 可用。
- 工程级 CSR/SSR 首屏切换可用，示例明确标注尚未使用框架运行时。

门槛：干净安装可构建，模式入口可运行，本机配置和产物不进入 Git。此前本地已有 9 项单元测试和 15 项三浏览器用例通过；用户要求暂停测试后不追加运行。

### 阶段 1：冻结最小语义契约与代表用例

先与用户确认，而不是直接开始大规模实现。

- 确认组件边界、默认值时序、props 写权限、对象状态语义、普通取值与持续读取的区别。
- 确认 children、key、列表回调、错误处理、客户端/服务端支持范围。
- 明确首版不支持的形式及相应错误，保留自然的逃生写法。
- 写出计数器、受控输入、可复用状态、可排序编辑列表四个完整用例与预期行为。

门槛：这些用例能仅用少量一致 API 表达；关键语义没有互相矛盾。未确认项写入决策列表，不能用类型断言或隐式特殊规则掩盖。

### 阶段 2：响应式与作用域内核

- 实现内部 state、derived、effect、依赖跟踪、动态依赖清理、相等性和批处理。
- 建立组件/分支/列表行所属作用域，明确 cleanup 的顺序和责任。
- 保证写入后立即读取一致，派生图不暴露错误的中间结果。
- 覆盖分支切换、菱形依赖、嵌套计算、循环和异常恢复。

门槛：不依赖 DOM 的行为测试通过；销毁后不再运行订阅；没有靠全局单例存放用户状态。内部 API 先满足语义，不急于全部公开。

### 阶段 3：Babel 编译器与最小变量语法

- 实现独立 compile 入口，识别导入绑定和作用域，接入 component、state、derived 的最小语法。
- 保留读取、赋值、前后自增、短路赋值、闭包、对象简写的求值次数与顺序。
- 处理导入别名和局部遮蔽；类型位置、属性名和无关变量不能误改写。
- 生成可定位诊断和 source map，先在一个局部组件中验证。

门槛：转换快照和实际执行结果同时正确，支持形式有正反例。禁止用正则替换作为变量语义实现，也不依赖不稳定的 TS7 Compiler API 才能编译。

### 阶段 4：客户端 JSX 与基础 DOM

- 编译静态 DOM 与动态文本/属性位置，接入已有响应式作用域。
- 实现 Fragment、原生事件、布尔属性、class/style、SVG、DOM ref 和清理。
- 组件初始化与局部更新分开，普通函数调用中读取的状态也能被运行时正确跟踪。
- 使用真实计数器替换第一部分原生探针。

门槛：三浏览器中更新位置正确、事件调用次数正确、卸载彻底；不通过重新执行整个组件掩盖缺失的依赖转换。

### 阶段 5：组件输入、组合与表单基本行为

- 完成参数解构、默认值、别名、rest、属性转发和回调最新值读取。
- 完成 children 和简单内容组合，定义 context 的查找与生命周期。
- 实现约定的受控/非受控输入模式、焦点、选择区、IME、checked 等 DOM 特例。
- 核实默认对象隔离、父子对象共享和只读边界。

门槛：输入框和复用组件用例自然可用；父组件更新不会意外重置编辑状态；类型提示与运行时含义一致，不能靠普遍 any 通过检查。

### 阶段 6：结构更新、列表与错误恢复

- 完成条件分支、稳定 key 列表、动态组件和各自的作用域销毁。
- 验证同 key 新对象、移动、插入、删除、重复 key、index 变化和行内状态。
- 完成既定的错误边界与恢复流程，明确事件异常和渲染异常的处理位置。
- 用可排序编辑列表等完整页面替换更多工程探针。

门槛：输入焦点和局部状态跟随正确的身份；删除后订阅释放；一次失败不会使后续更新图永久损坏。

### 阶段 7：真正的 SSR 与 hydration

- 为组件和 JSX 生成服务端 HTML，正确处理文本、属性、void 元素、布尔值和必要的序列化转义。
- 每个请求建立独立状态与作用域，服务端不执行 DOM 副作用。
- 确定稳定标记、客户端接管顺序、事件挂接、默认值和 ID 一致性。
- 明确 hydration mismatch 的诊断与恢复策略，验证接管不重建本应复用的节点。
- 让 example 的两种模式真正运行同一套框架 App，移除对应原生 DOM 探针。

门槛：禁用 JS 的 SSR 可阅读，启用后能交互；CSR 与 SSR+hydrate 行为一致；并发请求不串状态；转义边界和节点身份有实际验证。当前文档组合测试不能替代此门槛。

### 阶段 8：类型、编辑器与开发体验

- 完善自身 JSX namespace、元素属性、事件、泛型组件、联合 props 和声明输出。
- 专门处理实时绑定与 TS 控制流收窄的语义缺口，特别是跨回调判空和可辨识联合。
- 将框架专有诊断与 TS7 原生诊断接到开发流程；基础提示不依赖私有 TS 插件。
- 完成 Vite 插件、SSR 开发更新、清楚的错误展示和可用 source map。
- HMR 先保证正确销毁/重建，再按明确兼容规则保留状态。

门槛：编辑、重命名、构建、声明消费和调试都可用；至少在主力 WebStorm 和一个标准 TS7 客户端验证。安装依赖不等于编辑器体验已经完成。

### 阶段 9：稳定性、性能与生产边界

- 检查长时间挂载/卸载、依赖切换、列表更新、异常恢复和内存释放。
- 检查 SSR 注入边界、状态序列化、请求隔离和服务端资源清理。
- 建立冷启动、更新、列表、SSR 吞吐、bundle 体积与内存基线。
- 依据测量优化热点，保留简单可维护的实现，不为未经证实的性能收益增加层次。
- 文档化浏览器、Node、TS7 小版本支持矩阵与已知限制。

门槛：关键回归场景稳定、严重缺陷清零、指标达到事先确认的预算。预算在有基线后确定，不编造“比某框架更快”的结论。

### 阶段 10：包产物、发布流程与 RC

- 确定实际需要的 runtime、compiler、Vite adapter 等包边界；职责成立后再拆包。
- 检查 exports、ESM、tree shaking、声明、source map、helper ABI 和服务端/客户端代码隔离。
- 从打包产物建立干净消费项目，验证 CSR 与 SSR，不使用源码别名掩盖发布问题。
- 建立版本、变更说明、升级指引、许可证与贡献规则。
- 在用户授权后发布 RC 或预览版本，不在无人值守阶段擅自公开发布 npm 包。

门槛：外部消费项目能够复现安装与构建；发布内容准确、凭据不进入仓库；RC 有明确支持范围和已知限制。

### 阶段 11：真实试点与生产版本

- 选择至少一个有表单、列表、异步数据和 SSR/CSR 需求的真实使用场景。
- 跟踪实际问题，补充回归用例和迁移说明，验证故障定位与回滚流程。
- 对最终候选版本执行完整 CI、浏览器与平台矩阵及必要压力验证。
- 完成用户文档、API 参考、错误说明、示例和维护承诺。
- 经用户确认后发布首个生产版本，并安排明确的缺陷维护方式。

门槛：没有未解决的发布阻断问题；真实应用和干净包消费都验证通过；功能与限制可被使用者理解；版本能够回滚。只有到这里才可以称为生产可用。

任何里程碑失败，必须说明缺口；不能用后续文档、跳过测试或固定等待把阶段标成完成。

## 6. 长时间自主执行规则

用户确认本计划和第一阶段的关键语义后，可以按以下方式持续推进：

1. 开始阶段前读取本计划、AGENTS.md、当前源码和 Git 状态，确认前置阶段真正完成。
2. 每次选择一个可审阅的局部目标，实现后只运行相关检查；完整矩阵放在阶段门槛、CI 和预发布阶段。
3. 常规命名、文件组织和实现细节自主决定，不为每个小步骤反复请求确认。
4. 每个可用阶段更新本文状态，记录实现范围、验证证据、限制、提交号和下一步，再提交并推送。
5. CI 可后台运行，不持续空等或轮询；在依赖该结果或准备发布时读取结果并处理失败。
6. 遇到失败先定位原因，不删除有效测试、不隐藏诊断、不退回假实现。
7. 保留用户改动，不覆盖未知工作；只清理本阶段拥有的临时文件、进程和产物，不清理共享缓存。
8. 目录整理应排除 node_modules 和构建产物，避免 Windows 移动操作遍历 pnpm 链接目标。

必须停下来讨论的情况：

- 需要改变已确认的组件形态、响应式语义或重要公共 API。
- 正确性与关键性能预算冲突，需要改变总体方案。
- 需要新增外部服务、费用、凭据权限，或执行 npm 发布、生产部署等未授权动作。
- 出现无法判定归属的用户改动或不可安全处理的数据。
- 同一阻碍经定位仍无法推进，需要用户决策或外部条件变化。

自主执行不意味着跳过设计确认，也不意味着无人值守时可以放宽验收标准。当前还未开始这一轮长期执行。
