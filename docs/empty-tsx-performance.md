# 简单 TSX 的冷检查成本

2026-10-07，在 `b48a81e` 和正式 RC6 SDK 上继续研究。源码只有 `export const value = 1;`，但配置启用了 `jsxImportSource: "zerodep-js"`。原始数据、失败实验与验证结果见 [empty-tsx-performance.json](../reports/empty-tsx-performance.json)。常驻服务方向另见[后台服务研究](native-daemon-performance.md)。本轮没有替换正式 SDK 或修改应用配置。

## 根因已经具体到声明

固定版本 TS-Go 的 `tsc/internal/compiler/fileloader.go:843` 按 `ScriptKindTSX` 加入隐式 JSX runtime 导入，没有先要求 AST 实际包含 JSX。`ast.GetJSXImplicitImportBase` 从编译选项或文件 pragma 得到提供者。因此空 TSX 也会加载 `zerodep-js/jsx-runtime` 及其依赖。

加载后的完整检查需要验证声明是否合法。单 checker 声明级 trace 显示：

| 检查对象                         | 追踪时间 | 本次声明检查触发的实例化 |
| -------------------------------- | -------: | -----------------------: |
| core `jsx-runtime.d.ts` 整个文件 |  5.215 s |                        — |
| 其中 `HtmlAttributes`            |  2.410 s |                2,036,254 |
| 其中 `IntrinsicElements`         |  2.389 s |                1,747,563 |
| TypeScript `lib.dom.d.ts`        |  0.520 s |                        — |
| csstype                          |  0.144 s |                        — |

两处框架声明约占该 JSX 声明文件追踪时间的 92%。trace 加了声明级事件和计数，使用一个 checker；其绝对时间不与普通四 checker 命令混用。这行常量自身没有可见的重型类型计算。

`HtmlAttributes<K>` 通过 `keyof NativeProps<HTMLElementTagNameMap[K]>` 判断哪些标准内容属性已由原生 props 覆盖。为了得到这些键，检查器展开了复杂的可写属性、事件、property 等类型。`IntrinsicElements extends Elements` 又需要验证标签映射的接口和索引约束。

## 第一选择：用现有原生增量检查保留已验证结果

未改动的正式 SDK 已支持磁盘增量信息。本次每轮仍启动新 CLI 进程，并未跳过声明检查：

```powershell
node scripts/native/tsc.mjs -p <项目配置> --noEmit --incremental --tsBuildInfoFile <缓存路径>
```

| 操作                            |             整条命令耗时 |
| ------------------------------- | -----------------------: |
| 首次，缓存不存在                |                  4.417 s |
| 原样再次检查                    |                  0.225 s |
| 常量从 1 改为 2                 |                  0.246 s |
| 改为 `const value: string = 2`  | 0.242 s，正确报告 TS2322 |
| 修复源码错误                    |                  0.226 s |
| 在已加载 JSX 声明中加入错误类型 | 4.320 s，正确报告 TS2304 |
| 修复声明错误                    |    4.332 s，重新完整验证 |
| 首次改为真实 `<div />`          |                  2.216 s |
| 再修改该 JSX 属性               |                  2.232 s |

这说明增量检查能复用有效的声明诊断结果，并正确响应源码和库声明的变化。它不保存所有后续使用都需要的类型对象；真实 JSX 的首次或后续类型实例化仍可能较重。不能把常量的 0.2 秒推广成所有 JSX 编辑的速度。

## 冷检查优化一：延后不适用索引的属性求值

发现的上游实现顺序位于 `tsc/internal/checker/checker.go:checkIndexConstraints`：先调用 `getNonMissingTypeOfSymbol` 求属性类型，再进入 `checkIndexConstraintForProperty` 判断是否有适用的索引签名。

框架定义了自定义标签索引 ``[tag: `${string}-${string}`]``。普通 `div`、`input` 等名字不匹配这个索引，原实现仍提前展开了它们的完整 props。

原型将顺序改为：先取得属性名并判断适用索引，只有确实需要比较时才求属性类型。匹配的属性仍走原有类型约束检查，不删除 readonly 或绑定规则。

| 普通命令，不带统计参数 | 三轮中位数 |          范围 |
| ---------------------- | ---------: | ------------: |
| 空 TSX，原实现         |    4.451 s | 4.290–4.464 s |
| 空 TSX，索引按需求值   |    2.642 s | 2.623–2.692 s |

另一次包含一个真实 `<div />` 的探索，检查阶段从 4.199 s 降到 2.453 s。主示例单独使用这项优化时耗时差异很小，但类型对象和存活堆减少；绑定推导仍占主要关键路径。与前一轮诊断阶段按需绑定组合时，同一轮主示例检查阶段从 4.512 s 降到 3.507 s，命令从 5.079 s 降到 4.052 s。后一组仅单轮，不作为跨机器承诺。

验证包含普通与模板字符串索引、数字和 symbol 索引、静态属性、私有字段、继承索引冲突，以及现有 core/use 类型用例。重叠索引仍检查相应属性。该方向值得继续作为通用 checker 优化，但正式合入仍需更多上游编译器回归和跨平台验证。[研究补丁](../reports/typecheck-lazy-index-prototype.patch)

## 冷检查优化二：不含 JSX 时不隐式加载 runtime

另一个原型检查 AST 的 `SubtreeContainsJsx`，对没有 JSX 的框架文件省去隐式 runtime 导入。空 TSX 普通命令三轮中位数 0.597 s，范围 0.582–0.607 s。标准库和实际源码仍然检查。

这个结果不能直接作为透明优化发布，验证发现两项边界：

1. 只检查 AST 标记会使刚输入 `<` 时丢失标签候选。对有解析错误的不完整文件保留原路径后，空文件 → `<` → 标签名 → `bind:` → 移除 JSX 的 LSP 过程通过，错误属性类型仍有诊断。
2. JSX runtime 可能带入全局声明。用 `paths` 指向一个带 `declare global` 的 runtime，原实现能识别相应全局名字，原型则产生 TS2304。这是实际语义差异，不是计时噪声。

因此这条路线需要经过验证的、没有全局类型副作用的提供者契约，或更保守的原生加载设计。当前没有启用该规则。它主要改善真正不使用 JSX 的文件；项目中存在真实 JSX 或显式导入相关声明时，仍需支付相应类型成本。[研究补丁](../reports/typecheck-lazy-jsx-prototype.patch)

## 其他方案的取舍

- 普通类型语法重写，包括命名 `Mutable`、增加分支 helper、tuple 条件延迟、`infer`、拆分 HTML/SVG/MathML 映射，没有消除主要成本。键重映射版 `WritableKeys` 反而退化到约 7.9 s，暂不增加这些维护复杂度。
- `skipLibCheck` 对空 TSX 命令约 0.245 s。现有类型消费用例仍通过，但它会跳过声明文件自身的合法性检查，属于验证范围决策。可以研究消费者日常检查与库/CI 完整验证分工，不将其描述为同等检查范围的加速。
- 保持常驻后台并使用原生增量构建，比只保留进程更有效。当前服务的普通完整检查在改动后仍重建检查快照；增量构建已能正确复用有效诊断，见后台服务报告。

## 记录与复现边界

实验使用主目录内的临时声明副本和从固定提交构建的临时 SDK，没有工作树。原生补丁通过研究环境变量显式开关，未列入正式 `nativeInputs`。普通计时不含 trace/pprof，也不与 Go 构建并行；未清空 OS 文件缓存。三轮普通空文件计时的前两轮和第三轮原型二进制略有不同，第三轮仅增加不完整语法兜底及关闭状态的绑定开关，空文件的有效行为一致。

早期两项条件类型实验因为探针生成脚本定界错误产生语法错误，已修正并复测；失败记录保留，未计为性能收益。所有类型、配置、标准库和正式 SDK 均保持原样。临时源码、二进制、增量缓存和探针在取证后逐文件清理。
